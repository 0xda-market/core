# Broker payouts

Status: implemented by the payout replacement for superseded PR #97
Scope: `0xda-market/core`

## Contract

The broker economic invariant remains unchanged:

`broker ask = broker earning`

Marketplace pricing, routing headroom, settlement costs and market margin never reduce an earning after allocation. Payouts only move already-earned USDT through a separate ledger lifecycle.

The broker-facing workflow is deliberately small:

1. provide liquidity and choose an ask;
2. fulfill allocated paid orders;
3. configure one USDT payout destination and optional minimum payout threshold;
4. request payout of the currently available balance;
5. receive the transfer.

Core owns batching, ledger identity, concurrency and reconciliation. The broker never selects individual earning rows or edits a payout amount.

## Earnings lifecycle

```text
pending
  ↓ paid fulfillment succeeds
available
  ↓ atomically claimed into one payout
payout_queued
  ↓ payout transfer is confirmed
paid
```

`void` remains reserved for an explicit future reversal contract.

An earning belongs to at most one payout through `broker_earnings.payout_id`. Confirmation is allowed only when every attached earning is still `payout_queued`, belongs to the payout seller, uses the payout currency, and the exact attached earning sum equals the immutable payout amount.

## Payout profile

A broker configures:

- canonical payout currency: `USDT`;
- network;
- destination;
- minimum payout amount;
- enabled/disabled state.

The profile is an immutable domain record with optimistic concurrency. Creating a profile omits a version. Updating an existing profile requires its exact current version; stale or versionless updates are rejected.

Changing the profile never mutates a payout that already exists. Network and destination are snapshotted into each payout.

## Queueing and idempotency

A broker may have at most one payout in `queued` or `processing` state. Core serializes queue operations by locking that broker's payout-profile row before it reads payout or earning state. PostgreSQL also enforces the one-in-flight invariant with a partial unique index.

If an in-flight payout already exists, a repeated queue request returns that payout. Newly available earnings remain `available` for the next payout rather than being attached to an older amount snapshot.

For a new payout, all current `available` earnings are locked and claimed atomically. The payout amount is their exact USDT sum. The economic idempotency key is generated by core from:

```text
broker id + SHA-256(sorted earning ids)
```

The caller does not supply the economic idempotency key. This prevents a reused client key from attaching a new earning set to an old payout.

If the available total is below the configured threshold, no payout or earning state changes are committed.

## Manual-approved execution

The initial executor remains intentionally provider-neutral and custody-free:

1. core creates a `queued` payout;
2. an operator performs the external USDT transfer;
3. the authenticated operator API confirms the payout with an external reference and optional provider data;
4. core locks the payout and attached earnings, validates the complete ledger aggregate, then atomically marks both payout and earnings `paid`.

Confirmation is idempotent only for the already-recorded external reference. A paid payout cannot be rebound to a different reference.

The pair `(network, external_reference)` is unique for confirmed payouts. This prevents one transfer from accidentally paying two payout records while still allowing unrelated networks to use references with the same textual value.

A future wallet or custody adapter may introduce `queued → processing → paid | failed` without changing broker earnings or buyer pricing contracts.

## API surface

Broker self-service:

- `GET /v1/broker/earnings`
- `GET /v1/broker/balance`
- `GET /v1/broker/payout-profile`
- `PUT /v1/broker/payout-profile`
- `GET /v1/broker/payouts`
- `POST /v1/broker/payouts/queue`

Operator-only confirmation under the existing operator bearer-auth boundary:

- `POST /operator/v1/broker/payouts/:id/confirm`

The public and operator composition roots receive `broker_earnings` explicitly. Payout wiring never discovers dependencies through another service's instance variables.

## Database guards

Migration `017_broker_earnings.sql` created the earnings, profile and payout tables. This payout slice reuses that schema and adds only constraints that were absent because #97 was never merged:

- one `queued`/`processing` payout per seller;
- unique `(network, external_reference)` for non-null external references.

No pricing, recipient, bootstrap or automatic-pricing tables are changed.

## Invariants

- broker ask remains the broker earning;
- payout currency is canonical USDT in this version;
- payout/profile records validate domain state and are immutable;
- existing payout profiles require exact-version updates;
- a broker has at most one in-flight payout;
- queue requests never append new earnings to an existing payout amount;
- economic idempotency is core-owned and bound to the exact earning set;
- payout amount equals the exact sum of attached earnings;
- payout confirmation and earning payment happen in one transaction;
- a confirmed transfer reference cannot be reused on the same network;
- later marketplace, recipient, bootstrap and automatic-pricing contracts remain authoritative and untouched.
